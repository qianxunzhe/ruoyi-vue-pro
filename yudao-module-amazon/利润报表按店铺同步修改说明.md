# 利润报表按店铺同步修改说明

## 修改时间
2025-08-27

## 修改背景
原有的利润报表同步逻辑是一次性同步所有店铺的数据，可能会导致数据量过大，同步过程中出现问题时难以定位具体是哪个店铺的问题。

## 修改内容

### 1. 核心逻辑修改
修改文件：`ProfitReportServiceImpl.java`

#### 原逻辑
- 按天循环，每天一次性同步所有店铺的数据
- 执行顺序：日期循环 → 获取所有店铺数据 → 保存

#### 新逻辑
- 先按店铺循环，再按天循环
- 执行顺序：店铺循环 → 日期循环 → 获取单个店铺数据 → 保存
- 每个店铺独立同步，互不影响

### 2. 具体实现
```java
// 主要改动点
1. 新增 ShopsService 依赖注入
2. 修改 syncProfitReport 方法：
   - 外层增加店铺循环
   - 每个店铺单独调用API同步
   - 如果未指定店铺，自动获取所有活跃店铺
```

### 3. 同步流程
```
1. 刷新SKU-SPU缓存
2. 获取要同步的店铺列表
   - 如果指定了店铺ID，使用指定的店铺
   - 如果未指定，获取所有活跃店铺
3. 按店铺ID依次同步
   - 对每个店铺：
     a. 按天循环同步数据
     b. 调用API获取该店铺当天数据
     c. 根据同步类型处理数据（全量/增量）
     d. 保存数据
4. 统计总同步数量
```

## 优势

1. **更好的错误隔离**：某个店铺同步失败不会影响其他店铺
2. **更清晰的日志**：可以明确看到每个店铺的同步进度
3. **更灵活的控制**：可以针对特定店铺进行重试
4. **避免数据混乱**：每个店铺独立处理，数据不会混杂
5. **更易于监控**：可以监控每个店铺的同步状态

## 注意事项

1. 同步时间会比原来稍长，因为是逐个店铺同步
2. 建议在同步大量数据时分批进行
3. 可以通过指定店铺ID来针对特定店铺进行同步
4. 日志会更详细，便于追踪每个店铺的同步状态

## 后续优化建议

1. 可以考虑增加并发控制，允许多个店铺并行同步（需要控制并发数）
2. 可以增加同步进度的实时反馈机制
3. 可以增加失败重试机制，针对失败的店铺自动重试
